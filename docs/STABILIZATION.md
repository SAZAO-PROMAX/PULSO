# Checkpoints de estabilização
Pedido de 07/11/2026. Apenas dados fictícios. Preservar todos os ficheiros e alterações anteriores.
Git inicial: muitas alterações staged/untracked anteriores; sem user.name/user.email configurados. Não realizar commits parciais de ficheiros preexistentes nem atribuir autor inventado. Checkpoints são guardados no disco e aqui registados. O utilizador pode rever e criar o commit depois.
Etapa 1 em curso: launcher raiz npm run dev / dev.cmd, sem depender do PATH do Codex. Sem terminar automaticamente processos desconhecidos ou reutilizar uma API antiga.

Etapa 1: launcher conjunto testado com Node instalado em Program Files, sem caminhos de runtime do Codex. HTTP 200 em 8081, /health ativo em 8000; segunda instância recusada explicitamente. Corrigida variável CI herdada: string vazia era inválida para o Expo. QR gerado aponta para 127.0.0.1 e não é válido num telefone; os fluxos completos atuais são web. Diagnóstico de firewall apenas leitura, sem alterações ou exposição pública. Não foi testado um dispositivo físico. Dependências já instaladas. Commit não criado: index anterior e autor Git em falta.

Etapa 2: API passa a confirmar gravações numa base única .local/pulso.sqlite3, SQLite da biblioteca Python padrão, sem novas dependências. Transações por perfil impedem eliminações/gravações parciais. Cópia antiga localStorage é migrada uma vez e removida apenas após confirmação da API; erro conserva a cópia. Se a base já tiver alterações incompatíveis, a migração recusa sobreposição em vez de apagar trabalho. 6 testes reais de SQLite/API aprovados em bases temporárias, incluindo reabertura, originais, duplicados e âmbito por perfil. Sem login existente: cabeçalho de perfil verifica âmbito demonstrativo, não prova identidade. Commit não criado pelos motivos do checkpoint inicial.

Etapa 3: comparação passa a normalizar apenas etiquetas lexicais seguras (maiúsculas, espaços, acentos, símbolos de micromol), mantendo valores/unidades originais. Laboratório não separa séries comparáveis; unidade/método/amostra distintos continuam separados. Contagens de recuperados/representados/fora do período visíveis. Exclusões explicadas no Histórico. Casos pequenos A–J repartidos entre testes SQLite reais e teste de gráfico com 5 datas, ordem invertida, laboratórios diferentes, 2 medições no mesmo dia, unidade distinta e unidade não suportada. Sem deduplicação por data ou valor.

Etapa 4: ações no Histórico existente para editar valor/unidade/data da medição, título/origem do exame, eliminar medição ou exame completo. Confirmação explícita anuncia os resultados associados. Backend valida âmbito por perfil e aplica alterações num único commit SQLite; evidência original e versões anteriores das correções preservadas. Testes reais de transação e ensaios de interface de edição/eliminação passaram isoladamente; suite integral em conclusão. Cancelamento de importação continua sem gravação. Sem Arquivar.
Etapa 5: não existe login/registo de conta no código. Não foi criado sistema de autenticação, palavras-passe, emails ou serviço pago. Perfis são demonstrativos; o cabeçalho de âmbito NÃO autentica uma pessoa e não torna a aplicação adequada para dados reais. Identidade, sessões seguras, revogação e autorização de produção ficam pendentes.
Etapa 6: mantida a interface e identidade. Mensagens distinguem API indisponível, migração recusada e confirmação real; rascunhos/correções não são limpos após falha. Dados refrescados após gravar/editar/eliminar. Corrigida a invocação de fetch que falhava no browser; ensaios integrais apanharam o erro antes da entrega. Um problema de isolamento entre ficheiros de testes foi corrigido com fixture automática por teste, sempre numa base temporária, nunca na base local do utilizador.

Verificação final de reinício: .\dev.cmd executado numa base temporária tmp/restart-proof.sqlite3; API confirmou uma sessão com 2 observações; Ctrl+C parou frontend/backend; segundo arranque recuperou exatamente as 2 observações e a interface respondeu HTTP 200. Testado que segunda instância devolve erro 1. Corrigida a propagação do código de erro no atalho .cmd. Servidores de teste parados, portas libertas. Base .local do utilizador não usada por estes ensaios. Nenhum dispositivo físico ou regra de firewall foi alterado.

Conclusão: 46 testes aprovados (17 TypeScript, 17 API/PDF/SQLite, 10 Chromium, 2 estrutura), typecheck e compilação aprovados. Edição/eliminação passaram também na suite completa. Registos e originais recuperados via API; leitura fictícia recuperada após reiniciar processos. Checkpoint final em disco, sem commits por segurança do index/identidade. Servidores de teste parados; portas 8081/8000 livres para o utilizador arrancar com .\dev.cmd.
Pendente objetivamente: autenticação/contas reais e autorização de produção; ensaio num telefone físico da rede; desenvolvimento nativo completo do seletor PDF; resolução manual de eventual conflito de migração entre cópias antigas e base já alterada. Sem dados reais, serviços externos, OCR ou Arquivar.
